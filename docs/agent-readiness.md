# Agent readiness

How besidka.com answers AI agents, why each piece exists, and what the owner
still has to do outside this repository. Written for the
[isitagentready.com](https://isitagentready.com) scan, but the pieces matter
on their own: agents and agent tooling fetch these files whether or not a
scanner exists.

Related docs: `docs/seo.md` (canonical host, robots, sitemap),
`docs/mcp-server.md` (the `/mcp` server), `docs/security-audit-2026-10.md`
(the single rate-limit rule). The OAuth authorization server behind the
per-user MCP tools is implemented in `server/utils/auth.ts`.

### Auth metadata

Besidka is an OAuth 2.1 authorization server for one resource: the MCP server
at `/mcp`. The public read-only tools need no token. Per-user tools need an
access token for a signed-in Besidka user. This is lazy auth: a protected
`tools/call` without a valid token returns `401` with a `WWW-Authenticate`
header that carries `resource_metadata`, so a client that only wants the
public tools never authenticates.

| Piece | URL | Served by |
| --- | --- | --- |
| Authorization server metadata | `/.well-known/oauth-authorization-server` | Better Auth through `server/routes/.well-known/oauth-authorization-server.get.ts` |
| OpenID configuration | `/.well-known/openid-configuration` | Better Auth through `server/routes/.well-known/openid-configuration.get.ts` |
| Protected resource metadata | `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` | Better Auth through `server/routes/.well-known/oauth-protected-resource/` |
| Dynamic client registration | `/api/auth/oauth2/register` | Better Auth, RFC 7591, no user session needed |
| Consent page | `/oauth/consent` | The app |
| Scopes | `shared/utils/mcp-oauth-scopes.ts` | Identity: `openid`, `profile`, `email`, `offline_access`. Read: `chats:read`, `projects:read`, `memory:read`. Write: `projects:write`, `memory:write` |

The root protected resource document describes the origin
(`resource: "https://besidka.com"`, rewritten from Better Auth's output in
`server/routes/.well-known/oauth-protected-resource/index.get.ts`, because
RFC 9728 section 3.3 requires `resource` to equal the identifier the well-known
URL was built from), the `/mcp` document describes the MCP resource, and the
`401` `resource_metadata` points at the `/mcp` one.

The flow is authorization code with PKCE (S256). The issuer is
`https://besidka.com`. The routes at `/.well-known/oauth-*` replace the
`@nuxtjs/mcp-toolkit` 404 stubs, which `nuxt.config.ts` removes (the inline
`remove-mcp-toolkit-oauth-stubs` module). The MCP server card carries the same
information under `_meta["com.besidka/authorization"]`: a vendor key, because
the v1 server card schema has no authentication field. The card marks
authorization as `required: false`, because the public tools work without it.

#### `/auth.md` and the decision behind it

The WorkOS auth.md profile
([workos/auth.md](https://github.com/workos/auth.md)) is a protocol for
*agentic registration*: an agent registers itself with a service by an ID-JAG
identity assertion, a verified email, or an anonymous identity with a later
claim ceremony. The machine-readable half lives in the authorization server
metadata, in an `agent_auth` block (`skill`, `identity_endpoint`,
`claim_endpoint`, `identity_types_supported`, ...) plus the
`urn:ietf:params:oauth:grant-type:jwt-bearer` and claim grants. The file at
`/auth.md` is a prose recipe for the agent. Its only structural requirement,
as the isitagentready.com `auth-md` skill states it, is Markdown with an H1
that contains `auth.md`.

Besidka implements none of the registration flows. Agents cannot create
accounts, and OAuth dynamic client registration registers a client
application, not a user or an agent identity. So:

- `agent_auth` is **not** published in the authorization server metadata, and
  must not be. Its identity types (`anonymous`, `identity_assertion`,
  `service_auth`) describe flows that do not exist here.
- `/auth.md` **is** published, because its structure can be satisfied
  truthfully. The first paragraph says plainly that agentic registration is
  not supported. The rest covers audience (agents acting for an existing user),
  discovery from the `401`, client registration, PKCE authorization with
  consent, scopes, token use, revocation and a list of what is not supported.
  The body is built per origin in `server/utils/agent-discovery/auth-md.ts`
  and served by `server/routes/auth.md.get.ts` with open CORS and a one hour
  cache.

This is a judgment call. The scanner passes on the H1, and an agent reading the
file learns the truth at once. If it ever reads as scanner gaming, delete the
route, the util and their spec: nothing else depends on them. Never add
`agent_auth` or an ID-JAG section without building the flow it describes.
`/auth.md` is not in `config/agent-discovery-routes.ts`: that list is the
markdown negotiation allowlist for HTML pages, and `/auth.md` is already
markdown.

Review before this ships: tokens that read private chats raise the stakes.
Scope design, token storage and revocation, consent copy, rate limits and the
privacy-policy and DPIA update (`docs/legal/dpia.md`) belong to the OAuth
work, not to this document.

| Level | Needs |

| 2 | Level 1, plus AI bot rules and Content Signals |

Besidka has been at Level 4 since 2026-10-29. With `/auth.md` and the OAuth
metadata the `auth.md` check should pass. The A2A Agent Card stays not

OAuth branch ships to confirm what the scanner now requires. See
[Auth metadata](#auth-metadata) and the Web Bot Auth row for why neither of
the others applies.

## How it works

### Modules

- **`nuxt-llms`** serves `/llms.txt`. It is set to `prerender: false`.
  Content, notes and sections live in the `llms` key of `nuxt.config.ts`. The
  notes say, in plain words, that this file covers only the app and landing
  site, that docs and a blog are planned at `/docs` and `/blog` and are not
  published, and that Besidka has no public API.
- **`nuxt-agent-discovery`** serves the markdown twins, the negotiation, the
  `Link` header, the API catalog and the MCP Server Card. Only the routes in
  `config/agent-discovery-routes.ts` are negotiated. Private prefixes
  (`/chats`, `/profile`, `/files`, `/shared`) are excluded, so they never
  return markdown.
- **Our own routes** under `server/routes/.well-known/`: the v0.2.0 skills
  index and `SKILL.md` files, `ai-catalog.json`, `poppy.json`, the MCP server
  card and the OAuth metadata routes, plus `/auth.md` at the root.

### Markdown twins and negotiation

Each allowlisted page has a twin. Static pages use `/<page>.md`. Content
pages use `/raw/<collection>/<name>.md` (set per route with the `raw` option).
`Accept: text/markdown` on a page returns the twin. Responses carry
`Vary: Accept, User-Agent`.

The twins under `/raw/**` are route-cached for an hour. The cache key ignores
the query string: `server/plugins/cache-key-without-query.ts` sets
`event.node.req.originalUrl` to the bare path on `/` and `/raw/**` before the
cache handler reads it (Nitro keys on `originalUrl || url || path`, and a
`getKey` function cannot live in `routeRules` because they are serialized).
`?x=<random>` therefore reuses one KV entry instead of minting a new one. The
landing page never reads the query on the server, and UTM values are read from
`window.location` in the browser (`docs/analytics-utm.md`), so
`/?utm_source=x` is unaffected. The request path still carries the query, so
routing and rendering do not change.

A negotiated response at an HTML URL (`GET /byok` with
`Accept: text/markdown`) copies `Cache-Control: max-age=3600` from the raw twin
while the HTML page is `no-cache`.
`server/plugins/markdown-negotiation-cache-control.ts` resets it to `no-cache`
in `beforeResponse` for markdown that is not served from a `.md` or `/raw/`
URL.

`/` is route-cached, so `Accept: text/markdown` on `/` gets a 307 to
`/raw/index.md` instead of a negotiated body.

The landing page is built from MDC components, so the module's automatic twin
came out empty. `server/plugins/agent-discovery-landing.ts` hooks
`agent-discovery:document` and fills the body from
`server/utils/agent-discovery/landing-markdown.ts`. It also adds the key
guide list from the `keyGuides` collection.

### Redirects from content paths

The module derives canonical URLs from the Nuxt Content path, not from the
Vue route. For `content/guides/byok.md` that is `/guides/byok`, but the page
lives at `/byok`. `contentPathRedirects` in `config/agent-discovery-routes.ts`
adds 301s from `/guides/byok`, `/guides/memory` and `/legal/*` to the page
paths. Without them the module would advertise URLs that do not exist.
`/guides/**` stays in the allowlist for the key guide pages, whose content
path and route match.

### Skills and the digest contract

`skills/<name>/SKILL.md` is the source. `server/utils/agent-discovery/skills.ts`
reads the bytes at request time and computes `sha256:<hex>` of the exact bytes
it serves. The index lists that digest. Edit a `SKILL.md` and the digest
changes by itself on the next deploy. Nothing is stored or hand-updated.

The route depends on two module internals:

- `runtimeConfig.agentDiscoverySkills`, which lists the registered skills;
- the `assets:agentSkills` Nitro server-asset mount, which holds the files.

Re-check both on every `nuxt-agent-discovery` upgrade. If either changes, the
index goes empty or the files 404. The `besidka-overview` skill describes the
OAuth-protected tools and the scopes, so keep it in step with
`shared/utils/mcp-oauth-scopes.ts`.

### The prerender guard

Any `addPrerenderRoutes` call makes Nitro load the server bundle in Node.
The bundle imports `cloudflare:workers`, which Node cannot load, so the build
fails. `nuxt-llms` 0.3.1 has `prerender: false` for this reason. As a
backstop, a `nitro:build:before` hook in `nuxt.config.ts` registers a
`prerender:routes` handler that clears the route set. The side effect:
`pnpm run generate` produces nothing. That is fine, because the app is not a
static site.

## Ownership boundary for the future split

The owner plans a separate documentation app (probably Docus) at `/docs` and
a blog at `/blog` (maybe Astro with emdash), on the same apex as separate
Workers routed by path. Agents only look at the origin root, so the root app
keeps ownership of everything that is global.

The root app (this repo) owns:

- `/auth.md`.
- `/robots.txt` and `/sitemap.xml`. When the other apps ship, add their
  sitemaps as sitemap index entries.
- Everything under `/.well-known/*`.
- `/llms.txt`. It will link to `/docs/llms.txt` and `/blog/llms.txt`. It must
  not copy their content.
- The entries in `ai-catalog.json`. Add the docs MCP server and the blog
  feeds as entries when they exist.
- The product MCP server at `/mcp`: public product facts (models, prices,
  providers, key guides, legal pages) and the OAuth-protected per-user tools.
- The OAuth authorization server and its metadata. The docs app must not
  publish its own.

The docs app owns its own content:

- Docus already ships `nuxt-agent-discovery`, `nuxt-llms` and
  `@nuxtjs/mcp-toolkit`. It brings its own `/docs/llms.txt`, `/docs/mcp` and
  markdown twins. Do not hardcode docs content in this app.

Which MCP serves what:

| Endpoint | Serves | Status |
| --- | --- | --- |
| `/mcp` | Public product facts, plus per-user tools behind OAuth | Public tools live; per-user tools on `feat/mcp-oauth` |
| `/docs/mcp` | Documentation | Planned, in the docs app |

Cloudflare Workers routes: `besidka.com/docs*` and `besidka.com/blog*` go to
their own Workers, and everything else goes to this one. When that happens,
revisit the WAF allowlist and the rate-limit rule (see the runbook). Both are
zone-wide and match by path.

The current `llms.txt` says docs and blog are planned, not published. That is
deliberate. Change the note on the day each one ships, not before.

## Owner runbook

These steps are manual. None can be done from this repository.

### 1. Fix the WAF rule that blocks discovery files (done)

Applied on 2026-10-29 with the `cf` CLI (rule version 16). Read the live rule
with:

```bash
cf rulesets account-rulesets phases get http_request_firewall_custom -z besidka.com
```

The zone custom rule "URL attackers" (phase `http_request_firewall_custom`,
rule id `2589606d444141329b90fe0d8a14778b`) contained this clause:

```
(http.request.uri.path contains ".well-known")
```

It returned 403 for every discovery file in production. Preview hosts are
unaffected, so the preview looked fine while production failed. The clause is
now:

```
(http.request.uri.path contains ".well-known" and not (http.request.uri.path in {"/.well-known/api-catalog" "/.well-known/ai-catalog.json" "/.well-known/poppy.json"} or starts_with(http.request.uri.path, "/.well-known/mcp/") or starts_with(http.request.uri.path, "/.well-known/agent-skills/") or starts_with(http.request.uri.path, "/.well-known/skills/")))
```

To re-check it:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://besidka.com/.well-known/ai-catalog.json
curl -s -o /dev/null -w '%{http_code}\n' https://besidka.com/.well-known/zzz
```

The first must print 200 and the second must still print 403. On
2026-10-29 the allowlisted files returned 200, while `/.well-known/zzz`,
`/.well-known/security.txt`, `/x/.well-known/ai-catalog.json` and `/wp-admin`
still returned 403.

The same rule has other clauses that can block future public paths, for
example `contains "login"`, `contains ".key"`, `contains "debug"` and
`contains "uploads"`. Check every new public path against them before you
ship it.

### 1b. Allow the OAuth discovery files (open, needed before the OAuth branch ships)

The OAuth metadata routes live under `.well-known`, so the clause from step 1
returns 403 for them in production until the allowlist grows. Add the three
exact paths and the `oauth-protected-resource/` prefix (the `/mcp` resource
metadata). The full clause becomes:

```
(http.request.uri.path contains ".well-known" and not (http.request.uri.path in {"/.well-known/api-catalog" "/.well-known/ai-catalog.json" "/.well-known/poppy.json" "/.well-known/oauth-authorization-server" "/.well-known/openid-configuration" "/.well-known/oauth-protected-resource"} or starts_with(http.request.uri.path, "/.well-known/oauth-protected-resource/") or starts_with(http.request.uri.path, "/.well-known/mcp/") or starts_with(http.request.uri.path, "/.well-known/agent-skills/") or starts_with(http.request.uri.path, "/.well-known/skills/")))
```

Check the other new public paths against the rule's other clauses. Only four
clauses are known from this repo (`contains "login"`, `contains ".key"`,
`contains "debug"`, `contains "uploads"`), and the live rule was not readable
from the branch, so read it first with the `cf` command in step 1:

| Path | Matches a known clause? |
| --- | --- |
| `/auth.md` | No |
| `/oauth/consent` | No |
| `/api/auth/oauth2/register`, `/authorize`, `/token`, `/revoke`, `/userinfo`, and the JWKS path | No. None contains `login`, `.key`, `debug` or `uploads`. The authorize step redirects to `/signin`, which does not contain `login` either |

for path in /.well-known/oauth-authorization-server /.well-known/openid-configuration /.well-known/oauth-protected-resource /.well-known/oauth-protected-resource/mcp /auth.md; do

curl -s -o /dev/null -w '%{http_code}\n' https://besidka.com/.well-known/zzz

### 2. Cover `/mcp` and `/raw/` in the rate-limit rule (done)

Applied on 2026-10-29 with the `cf` CLI (rule version 4). Read the live rule
with the same command as step 1, using the phase `http_ratelimit`.

The zone is on the Free plan, which allows one rate-limiting rule. It is
"API flood limit" (rule id `80f1bc83826847c0bee7c09996b4af47`, see
`docs/security-audit-2026-10.md`). It did not match `/mcp` or `/raw/`. `/mcp`
is public and unauthenticated, and `/raw/` serves the markdown twins from a
content query on every cache miss. These clauses are now part of its
expression:

```
or starts_with(http.request.uri.path, "/mcp") or starts_with(http.request.uri.path, "/raw/")
```

`starts_with(..., "/mcp")` also covers `/mcp/`.

**Anthropic egress and the per-IP limit.** The limit is 100 requests per
10 seconds per IP, then block for 10 seconds
(`docs/security-audit-2026-10.md`). Claude connectors reach `/mcp` from
Anthropic's published egress range `160.79.104.0/21`, so many users share a
small pool of IPs, and the per-IP limit counts them together. A burst of
connector traffic can then block every Claude user for 10 seconds at a time.
The range comes from the task brief, not from an observation: confirm it
against Anthropic's current IP documentation before you act on it. If the
blocks show up, exclude the range from the `/mcp` clause only, for example
`(starts_with(http.request.uri.path, "/mcp") and not ip.src in {160.79.104.0/21})`,
and let the app-side limits on the protected tools do the work. The OAuth
endpoints under `/api/auth/oauth2/` are not in this rule, so Better Auth's
rate limiter is the only limiter there. Check its rules for those paths
(`docs/auth-security.md`) before the OAuth branch ships.

### 3. WebMCP origin-trial token (optional)

The 2026-10-29 preview scan detected the three WebMCP tools without a token,
so the scanner does not need one. Real Chrome users outside the trial flag
still do, so register one if you want WebMCP to work for them:

1. Register an origin-trial token for `https://besidka.com` at
   https://developer.chrome.com/origintrials.
2. Set `NUXT_PUBLIC_WEBMCP_ORIGIN_TRIAL_TOKEN` in the production Worker vars
   (`env.production.vars` in `wrangler.jsonc`).

`app/app.vue` emits the `origin-trial` meta tag only when the value is set.

### 4. DNS-AID (approved, open)

The owner approved enabling DNSSEC and the SVCB records. DNS-AID is in no
level gate, but the scanner has a check for it.

1. Enable DNSSEC: Cloudflare DNS, then DNSSEC. Add the DS record at the
   registrar. Wait for the DS record to propagate before step 2: SVCB records
   are only trustworthy when signed.
2. Publish the records. The current draft is
   [`draft-mozleywilliams-dnsop-dnsaid-02`](https://www.ietf.org/archive/id/draft-mozleywilliams-dnsop-dnsaid-02.txt)
   (May 2026, expires 2026-11-28). It adds no new record types: it uses SVCB
   (RFC 9460). Per the draft, an agent has an SVCB record whose `alpn` carries
   the transport and optionally the agent protocol, plus an optional
   `well-known` parameter with the well-known path, and an organization-level
   index sits at `_index._agents.<domain>` with a TargetName that contains no
   underscores. Proposed records:

```
_mcp._agents.besidka.com.   3600 IN SVCB 1 besidka.com. alpn="mcp,h2" port=443 well-known="mcp/server-card.json"
_index._agents.besidka.com. 3600 IN SVCB 1 besidka.com. alpn="h2" port=443 well-known="ai-catalog.json"
```

3. Re-scan (step 6).

Unverified parts. The draft is not final and the scan is the only judge:

- `well-known` and `cap` are not registered SvcParamKeys. Cloudflare DNS may
  refuse the names. If so, use the private-use `keyNNNNN="value"` syntax or
  leave the parameter out.
- `alpn="mcp,h2"` is the draft's own example, but `mcp` is not an IANA ALPN
  identifier. Plain `alpn="h2"` is the safe fallback.
- The draft leaves the content of the index to other standards, so pointing
  `_index._agents` at `ai-catalog.json` is a guess that matches the ARD
  catalog we already serve.
- The `_mcp._agents` name follows the earlier -01 wording and the draft's note
  that an operator may publish agents under an `_agents` leaf, where
  AliasMode SVCB must point at the primary owner. Use a plain
  `mcp.besidka.com` agent name and an AliasMode record at `_mcp._agents` if the
  scan rejects the direct form.
- No reference site passing the check was found.
