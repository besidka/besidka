# Agent readiness

How besidka.com answers AI agents, why each piece exists, and what the owner
still has to do outside this repository. Written for the
[isitagentready.com](https://isitagentready.com) scan, but the pieces matter
on their own: agents and agent tooling fetch these files whether or not a
scanner exists.

Related docs: `docs/seo.md` (canonical host, robots, sitemap),
`docs/mcp-server.md` (the `/mcp` server), `docs/security-audit-2026-10.md`
(the single rate-limit rule).

### Auth metadata (not done)

The scanner checks for OAuth or OIDC discovery, OAuth Protected Resource
metadata and `auth.md`. Besidka publishes none of them, on purpose.

Besidka is an OAuth **client** of Google and GitHub. It is not an
authorization server. Publishing `oauth-authorization-server` or
`oauth-protected-resource` metadata without a real authorization server would
tell agents to start a flow that cannot finish. The public `/mcp` server needs
no auth, so it has nothing to protect. `@nuxtjs/mcp-toolkit` registers JSON
404 stubs at those paths (see `docs/mcp-server.md`); they stay as they are.

The honest path is a future authenticated MCP server, for example one that
reads a user's own chats. That would need real work:

- `@better-auth/mcp`, built on `@better-auth/oauth-provider`. It needs
  `better-auth` `^1.7.14` (a bump), the `jwt()` plugin and `cimd`.
- New additive tables: `oauthClient`, `oauthResource`,
  `oauthClientResource`, `oauthAccessToken`, `oauthRefreshToken`,
  `oauthConsent`, `oauthClientAssertion` and `jwks`. Follow the migration
  rules in `AGENTS.md`: additive only, no `DROP TABLE`.
- A consent page and a login page for the authorization flow.
- Root routes at `/.well-known/oauth-*`. They must replace the toolkit 404
  stubs, which sit at the same paths.
- A security review. Tokens that read private chats raise the stakes: scope
  design, token storage and revocation, consent copy, rate limits and a
  privacy-policy and DPIA update (`docs/legal/dpia.md`).

Do not start this to raise a score. Start it when there is a private tool
worth exposing.

## Levels

The scanner assigns a level from the checks that pass:

| Level | Needs |
| --- | --- |
| 0 | Nothing |
| 1 | Two of: `robots.txt`, sitemap, Link headers |
| 2 | Level 1, plus AI bot rules and Content Signals |
| 3 | Level 2, plus Markdown negotiation |
| 4 | Level 3, plus any one of: MCP Server Card, A2A card, Agent Skills, API catalog |
| 5 | Level 4, plus two of three: Web Bot Auth, all integrations, auth metadata |

Besidka has been at Level 4 since 2026-10-29. Level 5 needs auth
metadata plus either Web Bot Auth or all integrations. None is planned. See
[Auth metadata](#auth-metadata-not-done) for why, and the Web Bot Auth row
for why that one does not apply.

## How it works

### Modules

- **`nuxt-llms`** serves `/llms.txt`. It is set to `prerender: false`.
  Content, notes and sections live in the `llms` key of `nuxt.config.ts`. The
  notes say, in plain words, that this file covers only the app and landing
  site, that docs and a blog are planned at `/docs` and `/blog` and are not
  published, and that Besidka has no public API.
- **`nuxt-agent-discovery`** serves the markdown twins, the negotiation, the
  `Link` header, the API catalog and the MCP Server Card. Only the routes in
  `config/agent-discovery-routes.ts` are negotiated. Private prefixes
  (`/chats`, `/profile`, `/files`, `/shared`) are excluded, so they never
  return markdown.
- **Our own routes** under `server/routes/.well-known/`: the v0.2.0 skills
  index and `SKILL.md` files, `ai-catalog.json` and `poppy.json`.

### Markdown twins and negotiation

Each allowlisted page has a twin. Static pages use `/<page>.md`. Content
pages use `/raw/<collection>/<name>.md` (set per route with the `raw` option).
`Accept: text/markdown` on a page returns the twin. Responses carry
`Vary: Accept, User-Agent`.

The twins under `/raw/**` are route-cached for an hour. The cache key ignores
the query string: `server/plugins/cache-key-without-query.ts` sets
`event.node.req.originalUrl` to the bare path on `/` and `/raw/**` before the
cache handler reads it (Nitro keys on `originalUrl || url || path`, and a
`getKey` function cannot live in `routeRules` because they are serialized).
`?x=<random>` therefore reuses one KV entry instead of minting a new one. The
landing page never reads the query on the server, and UTM values are read from
`window.location` in the browser (`docs/analytics-utm.md`), so
`/?utm_source=x` is unaffected. The request path still carries the query, so
routing and rendering do not change.

A negotiated response at an HTML URL (`GET /byok` with
`Accept: text/markdown`) copies `Cache-Control: max-age=3600` from the raw twin
while the HTML page is `no-cache`.
`server/plugins/markdown-negotiation-cache-control.ts` resets it to `no-cache`
in `beforeResponse` for markdown that is not served from a `.md` or `/raw/`
URL.

`/` is route-cached, so `Accept: text/markdown` on `/` gets a 307 to
`/raw/index.md` instead of a negotiated body.

The landing page is built from MDC components, so the module's automatic twin
came out empty. `server/plugins/agent-discovery-landing.ts` hooks
`agent-discovery:document` and fills the body from
`server/utils/agent-discovery/landing-markdown.ts`. It also adds the key
guide list from the `keyGuides` collection.

### Redirects from content paths

The module derives canonical URLs from the Nuxt Content path, not from the
Vue route. For `content/guides/byok.md` that is `/guides/byok`, but the page
lives at `/byok`. `contentPathRedirects` in `config/agent-discovery-routes.ts`
adds 301s from `/guides/byok`, `/guides/memory` and `/legal/*` to the page
paths. Without them the module would advertise URLs that do not exist.
`/guides/**` stays in the allowlist for the key guide pages, whose content
path and route match.

### Skills and the digest contract

`skills/<name>/SKILL.md` is the source. `server/utils/agent-discovery/skills.ts`
reads the bytes at request time and computes `sha256:<hex>` of the exact bytes
it serves. The index lists that digest. Edit a `SKILL.md` and the digest
changes by itself on the next deploy. Nothing is stored or hand-updated.

The route depends on two module internals:

- `runtimeConfig.agentDiscoverySkills`, which lists the registered skills;
- the `assets:agentSkills` Nitro server-asset mount, which holds the files.

Re-check both on every `nuxt-agent-discovery` upgrade. If either changes, the
index goes empty or the files 404.

### The prerender guard

Any `addPrerenderRoutes` call makes Nitro load the server bundle in Node.
The bundle imports `cloudflare:workers`, which Node cannot load, so the build
fails. `nuxt-llms` 0.3.1 has `prerender: false` for this reason. As a
backstop, a `nitro:build:before` hook in `nuxt.config.ts` registers a
`prerender:routes` handler that clears the route set. The side effect:
`pnpm run generate` produces nothing. That is fine, because the app is not a
static site.

## Ownership boundary for the future split

The owner plans a separate documentation app (probably Docus) at `/docs` and
a blog at `/blog` (maybe Astro with emdash), on the same apex as separate
Workers routed by path. Agents only look at the origin root, so the root app
keeps ownership of everything that is global.

The root app (this repo) owns:

- `/robots.txt` and `/sitemap.xml`. When the other apps ship, add their
  sitemaps as sitemap index entries.
- Everything under `/.well-known/*`.
- `/llms.txt`. It will link to `/docs/llms.txt` and `/blog/llms.txt`. It must
  not copy their content.
- The entries in `ai-catalog.json`. Add the docs MCP server and the blog
  feeds as entries when they exist.
- The product MCP server at `/mcp`: public product facts (models, prices,
  providers, key guides, legal pages).

The docs app owns its own content:

- Docus already ships `nuxt-agent-discovery`, `nuxt-llms` and
  `@nuxtjs/mcp-toolkit`. It brings its own `/docs/llms.txt`, `/docs/mcp` and
  markdown twins. Do not hardcode docs content in this app.

Which MCP serves what:

| Endpoint | Serves | Status |
| --- | --- | --- |
| `/mcp` | Public product facts | Live |
| `/docs/mcp` | Documentation | Planned, in the docs app |

Cloudflare Workers routes: `besidka.com/docs*` and `besidka.com/blog*` go to
their own Workers, and everything else goes to this one. When that happens,
revisit the WAF allowlist and the rate-limit rule (see the runbook). Both are
zone-wide and match by path.

The current `llms.txt` says docs and blog are planned, not published. That is
deliberate. Change the note on the day each one ships, not before.

## Owner runbook

These steps are manual. None can be done from this repository.

### 1. Fix the WAF rule that blocks discovery files (done)

Applied on 2026-10-29 with the `cf` CLI (rule version 16). Read the live rule
with:

```bash
cf rulesets account-rulesets phases get http_request_firewall_custom -z besidka.com
```

The zone custom rule "URL attackers" (phase `http_request_firewall_custom`,
rule id `2589606d444141329b90fe0d8a14778b`) contained this clause:

```
(http.request.uri.path contains ".well-known")
```

It returned 403 for every discovery file in production. Preview hosts are
unaffected, so the preview looked fine while production failed. The clause is
now:

```
(http.request.uri.path contains ".well-known" and not (http.request.uri.path in {"/.well-known/api-catalog" "/.well-known/ai-catalog.json" "/.well-known/poppy.json"} or starts_with(http.request.uri.path, "/.well-known/mcp/") or starts_with(http.request.uri.path, "/.well-known/agent-skills/") or starts_with(http.request.uri.path, "/.well-known/skills/")))
```

To re-check it:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://besidka.com/.well-known/ai-catalog.json
curl -s -o /dev/null -w '%{http_code}\n' https://besidka.com/.well-known/zzz
```

The first must print 200 and the second must still print 403. On
2026-10-29 the allowlisted files returned 200, while `/.well-known/zzz`,
`/.well-known/security.txt`, `/x/.well-known/ai-catalog.json` and `/wp-admin`
still returned 403.

The same rule has other clauses that can block future public paths, for
example `contains "login"`, `contains ".key"`, `contains "debug"` and
`contains "uploads"`. Check every new public path against them before you
ship it.

### 2. Cover `/mcp` and `/raw/` in the rate-limit rule (done)

Applied on 2026-10-29 with the `cf` CLI (rule version 4). Read the live rule
with the same command as step 1, using the phase `http_ratelimit`.

The zone is on the Free plan, which allows one rate-limiting rule. It is
"API flood limit" (rule id `80f1bc83826847c0bee7c09996b4af47`, see
`docs/security-audit-2026-10.md`). It did not match `/mcp` or `/raw/`. `/mcp`
is public and unauthenticated, and `/raw/` serves the markdown twins from a
content query on every cache miss. These clauses are now part of its
expression:

```
or starts_with(http.request.uri.path, "/mcp") or starts_with(http.request.uri.path, "/raw/")
```

`starts_with(..., "/mcp")` also covers `/mcp/`.

### 3. WebMCP origin-trial token (optional)

The 2026-10-29 preview scan detected the three WebMCP tools without a token,
so the scanner does not need one. Real Chrome users outside the trial flag
still do, so register one if you want WebMCP to work for them:

1. Register an origin-trial token for `https://besidka.com` at
   https://developer.chrome.com/origintrials.
2. Set `NUXT_PUBLIC_WEBMCP_ORIGIN_TRIAL_TOKEN` in the production Worker vars
   (`env.production.vars` in `wrangler.jsonc`).

`app/app.vue` emits the `origin-trial` meta tag only when the value is set.

### 4. DNS-AID (optional)

DNS-AID is in no level gate, so skip it unless you want the check.

1. Enable DNSSEC: Cloudflare DNS, then DNSSEC. Add the DS record at the
   registrar.
2. Publish SVCB records, for example:

```
_mcp._agents.besidka.com. 3600 IN SVCB 1 besidka.com. alpn="h2" port=443
```

   and an `_index._agents.besidka.com` record, per
   `draft-mozleywilliams-dnsop-dnsaid-01`.

The exact record values are unverified: no reference site that passes the
check was found. Confirm against the draft and a re-scan.

### 5. Cloudflare "Markdown for Agents" (not needed)

This Cloudflare feature is Pro and above. The zone is on Free. It would also
add its own `Content-Signal` header unless the origin sends one. The app
already negotiates markdown, so leave it off.

### 6. Re-scan

```bash
curl -s -X POST https://isitagentready.com/api/scan \
  -H 'content-type: application/json' \
  -d '{"url":"https://besidka.com"}'
```

## Validation

Run the same scan API against the PR preview host before production. The
preview does not have the WAF rule, so a pass there proves the app and says
nothing about step 1. Test production with the two `curl` commands in step 1.

Also check by hand:

```bash
curl -sI -H 'Accept: text/markdown' https://besidka.com/byok
curl -s https://besidka.com/.well-known/agent-skills/index.json
curl -s https://besidka.com/llms.txt
```

The first should return markdown (directly or through a 307 to the twin) with
`Vary: Accept, User-Agent`. Private paths such as `/chats` must never return
markdown.
